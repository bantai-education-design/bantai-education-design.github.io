# Ban.Tai 管理センター サーバー

設計・読み取り専用監査は [設計書](../../docs/admin-center/design.md)。GitHub Pagesだけでは安全なサーバー認証を提供できないため、編集サーバーを別途運用する。今回のPRは本番接続・デプロイを実行しない。

## ローカル検証

Node.js 24（node:sqlite使用）とnpmを用意し、このディレクトリで `npm ci`、`npm test`、`npm run build`。ブラウザー検証は `node test/browser.mjs`（PlaywrightとChromiumが必要）。CIはブラウザーをインストールして実行する。

ローカル手動確認には、リポジトリ外の永続ディレクトリとテスト専用パスワードハッシュを設定し、`ADMIN_DEV_HTTP=1`、`ADMIN_ORIGIN=http://127.0.0.1:8787`、`PORT=8787` を設定して `npm start`。開発HTTPモードはloopbackでのみ使用できる。本番用パスワードや本番GitHubトークンをローカル検証に使わない。`test/browser.mjs` は一時ディレクトリ・テスト専用資格情報を作成して自動削除する。

## 本番セットアップ（運用者が実施）

1. Node.js 24の常駐サーバーとHTTPSリバースプロキシを用意。サーバーは127.0.0.1にbindする。ホストOSの非管理ユーザーで起動し、外部から直接ポートへ到達させない。全API/画面/画像は同じHTTPS originから配信。プロキシで最大8MB・レート制限・タイムアウトを設定する。CORSは許可しない。
2. アプリ専用の永続ディレクトリをリポジトリ外に用意し、所有者のみアクセス可能にする。SQLite/WALとimagesが下書きの原本。サーバーレスの一時FSでは運用不可。
3. `node src/hash-password.js /リポジトリ外の保存先` をTTYで実行し、非表示入力でハッシュを生成する。平文パスワードをシェル引数・リポジトリ・チャットへ記載しない。生成された `salt:hash` をホスティングの秘密設定に登録。
4. 秘密設定 `ADMIN_PASSWORD_HASH`、`ADMIN_GITHUB_TOKEN` を登録。トークンは対象リポジトリのみ、Contents read/write、Pull requests read/write。GitHub App等の運用側でローテーションを行う。main保護・人間レビュー・必須CI・自動マージ禁止も設定する。トークンをブラウザーへ返すAPIはない。トークン未設定でも下書き編集は可能で、公開申請は明示的に失敗する。
5. 非秘密設定 `ADMIN_ORIGIN`（末尾スラッシュのないHTTPS origin）、`ADMIN_DATA_DIR`（外部絶対パス）、必要に応じ `PORT` を設定。`ADMIN_DEV_HTTP` は設定しない。ルートURLでログイン画面を提供し、`npm start` をsystemd等で常駐させる。ログへ環境変数やリクエスト本文を出力しない。
6. テスト用環境で認証、ログアウト、セッション期限、下書き再読込、画像、プレビュー、競合、復元を確認。公開申請は**公開リポジトリのPRに本文・使用画像が出る**ため、最初は公開してよいテスト内容のみで確認する。今回の自動テストはGitHub書込みをモックし、実際の公開PR作成は実行しない。
7. 接続確認後、Pagesの `admin/center-config.json` をPRで変更する。`enabled: true` と `url` にサーバールートのHTTPS URLだけを記載。秘密情報を追加しない。現状はdisabledで、写真機能だけをそのまま利用できる。
8. 運用者レビュー後にマージ・公開し、本番のログイン/公開申請→CI→人間承認→マージ→ページ反映を確認する。

## 運用と復旧

- 8時間セッション。CookieはSecure/HttpOnly/SameSite=Strict、セッション値のハッシュだけをDB保存。変更操作はOriginとCSRFを検証。誤ログイン5回で同一接続元IPを15分制限。プロキシ越しでは同じIPの利用者に制限が共有される。公開多人数サービス向け認証ではなく、単一運用者向け。
- HTTPSプロキシは受け取った `Origin` を書き換えず転送。外からのX-Forwarded-Forをログイン制限の識別子として信頼しない。サーバーの `/api/` をキャッシュしない。
- 定期バックアップはサービス停止中にデータディレクトリ全体（SQLiteとimages）を暗号化された非公開保存先へ取得する。復旧も停止中に全体を復元。公開リポジトリやPages配下へ置かない。保管容量・ディスク残量は運用側で監視し、無断で画像や履歴を消さない。
- 緊急停止はサービス停止＋Pages設定disabled。パスワード変更時はサービス停止中にSQLiteの `sessions` テーブルを空にし、既存セッションを失効させてから再開。GitHubトークンも漏洩疑い時に失効/交換する。
- 非公開化は管理対象記事を一覧から除き、HTMLを非公開案内に置換するPR。画像・原本・過去版を物理削除しない。GitHub履歴やキャッシュからの完全消去ではない。
- 復元は履歴の本文を**新しい下書き世代**として保存。公開済み内容は再申請・マージまで変わらない。
- PRを作っただけでは公開済み扱いにしない。公開履歴の「GitHubの状態を更新」でマージ/取り下げを確認する。配信成功はGitHub Pagesで別途確認。未完了PRがある間は次のコラム公開を止め、一覧の競合を避ける。GitHub API失敗時はGitHub側に部分的なブランチ/PRが残っていないかを確認してから再試行する。

## この段階の範囲

- 新規・既存コラムの本文内編集（文章、H2/H3、太字、リンク、画像、表、棒グラフ）、自動保存、プレビュー、公開/非公開PR申請、下書き履歴復元。
- 見出しボタンはH2、小見出しボタンはH3を切り替える。外部貼り付けはプレーンテキスト化し、トラッキング画像や任意HTMLを取り込まない。表はセル結合を提供しない。グラフは非負数の比較用。
- 既存記事は「編集する」で同じmainコミットから取り込む。原本HTML50件・本文型のみ10件の計60件を検証済み。段落・見出しと文書枠を保持し、変換できない画像・表・独自レイアウトは原本保持ブロックとして残す。元HTMLのある記事は同じURLを更新し、本文型のみの記事は同じIDで独立記事URLへ移行する。元記事の一覧情報・HTMLを非公開SQLiteへ保存する。原本はGit履歴にも残る。公開バックアップファイルを追加しない。
- 外部から元記事が更新されていた場合はハッシュ照合で停止する。「最新版を再取込」は現在の下書きを残して別の下書きを作る。履歴復元後の再公開もマージ確認後に行える。原本保持ブロック自体の内部編集は未対応（新しい文章・画像・表・グラフは挿入可能）。
- 大学DBは東京2校・神奈川36校・埼玉28校の完成形プロフィールを選択し、説明文・設置者・入試関連URLなどの限定項目を修正できる。「DB反映を申請」は出典確認と最新mainの変更前値の照合後、対象プロフィールと提案を同じPRに含める。構造化した学部・学生数・所在地、完成形未対応の大学は「提案だけをPRにする」で既存パイプラインの確認へ渡す。マージは自動化しない。
- 写真審査は現在のJotformと既存補正・ZIP生成を再利用。Jotformや既存写真ページのアクセス制御を、このサーバーのセッションに統合してはいない。既存写真ページは公開されたクライアント処理ツールで、非公開受信箱の認証はJotformに依存。
- 本番ホスティング、秘密設定、GitHub App作成、外部実環境接続、既存記事の本番移行はこのPRで実施しない（取り込み・編集・移行PRの生成機能は実装済み）。単一運用者向けで、複数アカウント/SSO/MFAは未実装。
